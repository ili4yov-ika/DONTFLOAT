# Система тестирования DONTFLOAT

## Обзор

Система тестирования DONTFLOAT включает функциональные тесты, тесты BPM анализа, синтетические тесты и диагностические инструменты.

## Структура тестов

```
tests/
├── test_bpm/                    # Тестовые аудиофайлы
│   └── example_80BPM.mp3       # Пример файла для тестирования BPM
├── CMakeLists.txt              # Конфигурация CMake для тестов
├── README.md                   # Документация тестов
├── test_bpm_analysis.cpp       # Полная система тестирования BPM
├── simple_synthetic_test.cpp   # Синтетический тест
├── functional_test.bat         # Функциональный тест
├── ui_diagnostic_test.bat      # Диагностика UI
├── color_fix_test.bat          # Тест цветовых схем
├── dark_theme_fix_test.bat     # Тест темной темы
├── ui_fixes_test.bat           # Тест исправлений UI
└── updated_functional_test.bat # Обновленный функциональный тест
```

## Синтетические тесты

### Генерация тестовых данных
```cpp
// Создание синусоидального сигнала с битами
const float testBPM = 80.0f;
const float duration = 5.0f;
const int totalSamples = static_cast<int>(sampleRate * duration);

for (int i = 0; i < totalSamples; ++i) {
    float sample = 0.0f;
    
    // Основной тон (440 Hz)
    sample += 0.3f * std::sin(2.0f * M_PI * 440.0f * i / sampleRate);
    
    // Биты (короткие импульсы)
    if (i % samplesPerBeat < samplesPerBeat / 10) {
        sample += 0.8f * std::sin(2.0f * M_PI * 880.0f * i / sampleRate);
    }
    
    // Шум для реалистичности
    sample += 0.1f * ((float)rand() / RAND_MAX - 0.5f);
    
    samples.append(sample);
}
```

### Преимущества синтетических тестов
- Независимость от внешних файлов
- Предсказуемые результаты
- Быстрое выполнение
- Легкая настройка параметров

## Правка высоты нот при растяжении

`tests/pitch_note_stretch_test.cpp` — интеграционный, на реальном
`pitch-test_C140BPM.mp3`. Детектор находит в файле одну устойчивую ноту (E3,
~165 Гц), пианорольный разрез делит её на восемь, после чего:

1. двум случайным нотам высота поднимается на два полутона, двум другим —
   опускается; результат меряется **по звуку** (автокорреляция), а не по полям
   структуры;
2. метки растягивают первую треть дорожки в полтора раза и сжимают вторую;
   ноты едут за метками, длительности меняются в тех же пропорциях, а тон
   остаётся прежним;
3. внутри растянутого и сжатого участков высота правится ещё раз — коррекция
   обязана работать уже по новым координатам.

Выбор нот случайный, но посев фиксированный: иначе тест мигал бы от прогона к
прогону.

Про допуски: на «тон не поехал после растяжения» — 6% (MP3 плюс Rubber Band),
на проверку самого сдвига — 2.5%. Второй специально строже: полутон это 5.95%,
и с допуском 6% проверка «нота уехала на два полутона» одинаково принимала бы
и один, и три.

В CI тест пропускает себя, как и `pitch_compensation_file_test`: декодер и
Rubber Band зависят от окружения.

## Каретки и транспорт в окне плагина

`tests/plugin_transport_sync_test.cpp` — полная редакция целиком, с настоящей
волной и пианороллом:

- щелчок по волне ведёт каретку пианоролла и наоборот (расхождение до 1 мс
  неизбежно: позиция ходит между половинами через сэмплы источника);
- кнопки ▶ ■ просят транспорт у хоста и, когда его нет, говорят об этом
  статусом, а не поднимают свой проигрыватель.

Окна на экране тест не ждёт (`qWaitForWindowExposed`): под CTest сеанс без
активного рабочего стола окно не показывает, и ожидание просто выходит по
таймауту. Синтетическим щелчкам `QTest` окно и не нужно — нужны разложенные
размеры виджетов.

## Два экземпляра в одном документе ARA

`tests/mini_daw_two_tracks_test.cpp` поднимает документ ARA на фабрике
плагина и сажает на две дорожки два экземпляра. Кроме своего звука и
референсных нот тут закреплены три вещи:

- выделение чужого клипа в DAW не уводит экземпляр с его дорожки
  (`testForeignSelectionDoesNotStealTheTrack`);
- каждый экземпляр находит **свой** клип (`testOwnClipIsFoundForEachInstance`);
- просьбы транспорта доходят до хоста (`testTransportRequestsReachTheHost`) —
  это тот самый путь, по которому идут кнопки ▶ ■.

## Интеграционный тест с настоящей DAW (REAPER)

`tests/reaper_ara_integration_test.cpp` плюс сценарий `tests/reaper/dontfloat_ara_probe.lua`.

Если REAPER на машине не найден, тест пропускает себя — в CI и на чужих
сборочных машинах он молчит. Ищется он в записи установщика (реестр) и в
обычных каталогах Program Files.

### Что делает

1. Кладёт сценарий в `%APPDATA%\REAPER\Scripts\__startup.lua`; чужой сценарий,
   если он там был, откладывается и возвращается на место после прогона.
2. Запускает REAPER, тот собирает проект: две дорожки, на каждой своё аудио,
   VST3 DONTFLOAT на первой и DONTFLOAT Pitcher на второй.
3. Режет клип пополам, переносит половину, растягивает и сжимает клип второй
   дорожки.
4. Читает дневник плагина и проверяет, что всё это до плагина дошло.

### Дневник плагина

Изнутри хоста плагин о себе не рассказывает: параметров у него нет, а
ARA-события, обмен нотами и порядок выгрузки живут внутри процесса DAW.
Поэтому плагин пишет их построчно в файл — `plugins/core/dontfloat_diagnostics.h`.

Включается переменной окружения:

```powershell
$env:DONTFLOAT_DIAG_FILE = "$env:TEMP\dontfloat_diag.txt"
```

Без неё каждый вызов выходит первой же строкой, так что в обычной работе DAW
это ничего не стоит. Заголовок сделан header-only намеренно: писать в дневник
нужно из мест, которые собираются в разные цели (приложение, плагины, тесты),
и отдельный `.cpp` пришлось бы добавлять в каждую цель отдельно.

Что пишется:

| Событие | Когда |
|---|---|
| `ara.region.add` / `ara.region.update` | клип поставили на дорожку, разрезали, подвинули, растянули |
| `ara.notes.parsed` | разбор источника завершён, ноты в модели |
| `ara.notes.reference` | ноты отданы соседнему источнику как референс |
| `ara.audio.applied` | волна забрала звук из документа ARA |
| `ara.clip.sync` | размещение клипа перечитано после правки (звук не трогали) |
| `ara.grid.applied` | тактовая сетка пришла из хоста |
| `ara.host.playback=1/0` | отдал ли хост плагину управление транспортом |
| `ara.source.unknown` | экземпляр не нашёл своей дорожки (ни клипов, ни выбора) |
| `ara.render frames=N regions=N` | сколько кадров выдал ARA-рендерер и сколько у него клипов |
| `notes.publish` / `notes.consume` | общая доска нот (вне ARA) |
| `shutdown.*` | этапы выгрузки плагина |

### Что важно знать про REAPER и ARA

- **Правки клипов обязаны идти внутри `Undo_BeginBlock` / `Undo_EndBlock`.** Без
  фиксации транзакции REAPER не рассылает ARA-уведомления, и до плагина не
  доходит ничего: сценарий отработает со `status=ok`, а дневник останется
  пустым.
- **Один и тот же файл на двух дорожках — это один ARA-источник.** Разбор
  пройдёт единожды, и референсным нотам будет неоткуда взяться: сосед у
  источника один, он сам. В сценарии поэтому два разных файла.
- **Референсные ноты подтягивает пианорольный редактор**, а в полной редакции
  он на отдельной вкладке и сам не открывается. Поэтому на второй дорожке
  стоит редакция Pitcher.
- **Плагин вешается на клип, а не на дорожку** (`TakeFX_AddByName`). На
  дорожке REAPER не назначает ARA-рендереру ни одного клипа —
  `ara.render regions=0`, — и экземпляр не знает ни своего звука, ни своей
  разметки.
- **Кнопки плагина сценарием не нажать**: окно рисует Qt, и ReaScript до его
  кнопок не дотягивается. Поэтому здесь проверяется только доступность
  интерфейса транспорта (`ara.host.playback=1`), а путь «кнопка → хост»
  закрыт мини-DAW: `mini_daw_two_tracks_test`.
- **Плагины в DAW — установленные, а не из дерева сборки.** После правок в
  коде их надо переустановить, иначе тест прогонит прошлую версию:
  `tools\build_windows_installer.bat`, затем
  `tools\install_plugins_windows.ps1` (просит права администратора).
